# Принятые архитектурные решения

Формат записи: контекст → решение → последствия → что рассмотрено и отвергнуто. Решение меняется только новой
записью в этом файле, а не правкой старой: история важнее аккуратности.

---

## Р-1. Строим обёртку на нативном SDK, а не на legacy WebView-SDK

**Дата:** 8 сентября 2026.

**Контекст.** У VK Карт два поколения мобильных SDK. На `dev.vk.ru` описано старое: Android
`ru.mail.maps:mapkit`, iOS `MapsSDK` 1.1.48 — это WebView вокруг JS-карты. Актуальное поколение — нативное
(`VKMapsSDK`/`MapsNativeSDK` на iOS, `com.vk.maps:maps-native-sdk` на Android, рендер Metal/Vulkan), на сайте оно
не описано, API берётся из DocC-архива.

**Решение.** Плагин строится на нативном поколении.

**Последствия.** Часть документации неприменима напрямую и служит только ориентиром. Android заблокирован до
получения координат выкладки (см. `platform-matrix.md`). Кластеризации в нативном SDK нет — делаем на Dart.

**Отвергнуто.** Legacy WebView-SDK: производительность WebView-карты, поколение заморожено (последний релиз —
апрель 2024), а бинарники по ссылкам из документации отдают 404.

## Р-2. Мост Dart ↔ native — Pigeon, контракт общий для платформ

**Дата:** 8 сентября 2026.

**Контекст.** Поверхность API большая: камера, маркеры, стили, источники, слои, события. Ручной `MethodChannel`
означает ручную сериализацию десятков моделей. Отдельный вопрос — держать описание контракта единым или по файлу
на каждый платформенный пакет (как в `google_maps_flutter`).

**Решение.** Pigeon; файл контракта один, живёт в `vk_maps_mapkit_platform_interface`.

**Последствия.** Android и iOS реализуют одинаковый набор методов. Там, где платформа не умеет что-то из
контракта, метод честно отвечает «не поддерживается на этой платформе», и это фиксируется строкой в
`platform-matrix.md`, а не тихой заглушкой. Расхождение возможностей у платформ уже известно (на iOS
документированы кластеризация, пробки, изолинии, на Android — базовая карта), поэтому таблица поддержки
обязательна.

**Отвергнуто.**
- Контракт по файлу на платформу (подход Google): честнее показывает расхождения, но контракт начинает
  расползаться с первого же дня. Разделить общий контракт позже дёшево, слить два обратно — нет.
- Биндинги через `dart:ffi` с кодогенерацией (подход `yandex_maps_mapkit`, 1199 сгенерированных файлов):
  оправдано при их размере SDK и наличии IDL. У VK публичного IDL нет, поверхность на порядок меньше, а FFI
  добавляет ручное управление памятью и работу с изолятами.

## Р-3. Нативный SDK подключается как `implementation`, а не `api`

**Дата:** 8 сентября 2026.

**Контекст.** В Gradle способ подключения зависимости определяет, видит ли приложение классы нативного SDK VK
напрямую. `yandex_maps_mapkit` использует `api` — их SDK открыт приложению.

**Решение.** `implementation`: нативный SDK спрятан за Dart-API плагина.

**Последствия.** Подъём версии SDK не ломает приложения потребителей. Если пользователю не хватает возможностей,
правильный путь — добавить метод в наш API, а не дописывать нативный код в обход плагина.

**Отвергнуто.** `api`: даёт гибкость, но делает нативный SDK частью нашего публичного контракта — после этого
любая смена версии потенциально ломающая, и закрыться обратно можно только мажорным релизом. Открыть доступ
позже, наоборот, можно в любой момент без слома.

## Р-4. Federated-структура из пяти пакетов

**Дата:** 8 сентября 2026.

**Контекст.** В одном репозитории — виджет карты, контракт, две нативные реализации и REST-клиент.

**Решение.** `vk_maps_mapkit` (фасад), `vk_maps_mapkit_platform_interface`, `vk_maps_mapkit_android`,
`vk_maps_mapkit_ios`, `vk_maps_api`.

**Последствия.** REST-клиент ставится без Flutter и тестируется без устройств. Платформы публикуются
независимо, а порядок публикации фиксирован в `publishing.md`.

## Р-5. iOS подключается и через CocoaPods, и через SPM; web в 0.1.0 не поддерживаем

**Дата:** 8 сентября 2026.

**Контекст.** Приложения-потребители сегодня живут в обоих вариантах сборки iOS. В `flutter/packages` — 19
файлов `Package.swift` на 20 подспеков, то есть двойное подключение стало нормой.

**Решение.** Плагин отдаёт и `.podspec`, и `Package.swift`. Версия нативного SDK задаётся в одном месте и
сверяется тестом, чтобы не разъехалась между режимами. Web-платформа в первом релизе не поддерживается.

**Последствия.** В CI две ветки сборки iOS. Имена фреймворков в двух режимах различаются — разводится флагом
компиляции в подспеке, как это сделано в `google_maps_flutter_ios_sdk10`.

**Отвергнуто.** Только подспек: технически работает везде (приложение с SPM откатывается на CocoaPods для такого
плагина), но приложение, включившее SPM ради отказа от CocoaPods, из-за нас не сможет удалить `Podfile`.

## Р-6. По Android объявляем пол версий и проверяем две точки, а не матрицу

**Дата:** 8 сентября 2026.

**Контекст.** Наш Android-код собирается внутри сборки приложения, поэтому версии Gradle, AGP, KGP и JDK задаёт
пользователь, а не мы. Вопрос был, насколько широкую совместимость обещать: полную матрицу AGP × KGP × Gradle ×
JDK с прогоном по всем углам или объявленный минимум.

**Решение.** В README и `platform-matrix.md` объявляется пол: AGP 8.x, KGP 1.9, Gradle 8.x, JDK 17. В CI
гоняются две сборки example — на полу и на текущих версиях. Отдельно проверяется, что плагин подключается и в
приложении на Groovy DSL, и на Kotlin DSL.

**Последствия.** Пользователь ниже пола получает внятный отказ, а не ошибку компиляции. Возможен пропуск поломки
на промежуточной комбинации версий; принимаем этот риск — ломается обычно на границах, а не в середине.
Поднять или опустить пол можно минорным релизом, публичный API это не затрагивает.

**Отвергнуто.** Полная матрица: десятки комбинаций в CI ради приложений, которые и без нас не соберутся на
актуальном Flutter (он сам требует JDK 17 и AGP 8.x).

## Р-7. Логотип VK на карте не скрывается — параметра видимости в API не будет

**Дата:** 8 сентября 2026.

**Контекст.** Нужно было решить, давать ли приложению возможность убрать логотип VK с карты. Проверено по
DocC-архиву нативного iOS SDK из релиза 1.4.4.14633 и по документации Android:

- `MapLogoAlignment` имеет ровно четыре варианта: `bottomLeft`, `bottomRight`, `topLeft`, `topRight`. Вариантов
  вроде `none` или `hidden` нет.
- У `MapView` из логотипных членов только `logoAlignment`, `logoIgnoresSafeArea`, `logoInsets` — свойства
  видимости не существует. При этом соседние элементы скрываются штатно: `showsCompass`, `showsZoomButtons`,
  `isCurrentLocationButtonVisible`. Отсутствие такого свойства именно у логотипа выглядит намеренным.
- На Android `LogoConfig` состоит из выравнивания и отступов, поля видимости нет.

**Решение.** В публичном API плагина отдаём только выравнивание и отступы логотипа. Параметра «скрыть логотип»
нет, и добавлять его нельзя.

**Последствия.** Виджет `VkMap` не получает флага видимости логотипа. Если такой запрос придёт от пользователей,
ответ — отказ со ссылкой на это решение, а не обходной путь.

**Отвергнуто.** Перекрытие логотипа Flutter-виджетом поверх карты: технически возможно, но это обход требования
атрибуции, а не поддерживаемая возможность SDK.

## Р-8. Android строится на документированном SDK `ru.mail.maps.sdk`

**Дата:** 8 сентября 2026.

**Контекст.** Решение Р-1 говорит строить обёртку на нативном поколении SDK.
На iOS это выполнимо: SDK доступен, API описан в DocC. На Android нативного
SDK нет ни в документации (описан только `ru.mail.maps:mapkit`), ни в
публичной выкладке — координаты запрошены у вендора. Ждать ответа, ничего не
делая, значит остановить половину работы на неопределённый срок.

**Решение.** Android-реализация пишется по документированному API
`ru.mail.maps.sdk`: `MapGlobalConfig`, `MapView.getMapAsync`, методы объекта
`Map`. Расхождения с iOS фиксируются в `platform-matrix.md`, а методы,
которых на Android нет, отвечают ошибкой `unsupported`.

**Последствия.** Часть контракта на Android не поддержана (границы видимой
области, проекции, изображения стиля, JSON-стиль, режимы следования).
Собрать и запустить Android-часть нельзя, пока не появится доступ к
артефакту: код написан по документации, но не проверен на устройстве.

**Отвергнуто.** Ждать ответа вендора и не писать Android вовсе: контракт и
фасад всё равно нужно проверять на двух платформах, а переписать маппинг под
другое поколение SDK дешевле, чем начинать с нуля.

## Р-9. Источник истины по API iOS SDK — модуль, а не DocC

**Дата:** 8 сентября 2026.

**Контекст.** Контракт и Swift-код писались по DocC-архиву из дистрибутива —
другой документации нативного iOS SDK нет. Первая же сборка примера
показала, что DocC и сам модуль расходятся:

| В DocC | В `.swiftinterface` |
| --- | --- |
| `MapAnimationEasing` | `MapCameraAnimationEasing` |
| `MapCameraAnimationResult.finished` | `.ended` |
| `CameraMovingPhase.singeCompleted` | такой случай отсутствует |
| `MapConfiguration.CameraMode.free` | `.perspective` / `.earth` |
| `MapDataSourceType.geojson` | `.geoJSON` |
| `MapView.cleanup()` | метода нет |
| `camera.minZoom` / `maxZoom` — изменяемые | только чтение, есть `setZoomRange` |

**Решение.** При расхождении верим `.swiftinterface` из xcframework, а не
DocC. Перед правкой нативного кода имя и сигнатуру проверяем в модуле:

```bash
grep -n "enum MapCameraAnimationEasing" \
  packages/vk_maps_mapkit/example/ios/Pods/VKMapsSDK/MapsNativeSDK.xcframework/\
ios-arm64_x86_64-simulator/MapsNativeSDK.framework/Modules/\
MapsNativeSDK.swiftmodule/arm64-apple-ios-simulator.swiftinterface
```

**Последствия.** Таблица в `native-api-surface.md` перепроверяется по модулю
при каждом подъёме версии SDK. Сборка примера — обязательная часть проверки,
а не финальный шаг: без неё расхождения не видны.

## Р-10. Web поддерживается с первого релиза

**Дата:** 9 сентября 2026.

**Контекст.** Решение Р-5 отложило web «до после 0.1.0». Причина в нём не записана, а по факту она была одна:
объём работы при заблокированном Android. Между тем web — единственная платформа VK Карт, у которой SDK
и документирован (111 методов `Map`, 48 событий), и доступен без переговоров с вендором: `MMR GL JS`
скачивается с `maps.vk.com/sdk/js/0/mmr-gl.js` и работает по ключу доступа.

**Решение.** Web входит в 0.1.0 шестым пакетом `vk_maps_mapkit_web`. Контракт остаётся общим: web-пакет
реализует тот же `VkMapsPlatform`, что и мобильные, но без Pigeon — моста в натив на web нет, вызовы идут
прямо в библиотеку на странице.

**Последствия.** Публичный API плагина не меняется: приложение получает ту же `VkMap`. Проверять реализацию
можно на машине разработчика — в отличие от Android, где нет даже артефакта. Появляется третья платформа
в матрице поддержки и в чек-листе живой проверки.

**Отвергнуто.** Ждать 1.0.0: web-часть не трогает нативные пакеты и не может их сломать, а откладывание
означало бы, что единственная полностью доступная платформа выходит последней.

## Р-11. Источник истины по web-SDK — сборка библиотеки, а не документация

**Дата:** 9 сентября 2026.

**Контекст.** При реализации web-пакета документация `dev.vk.ru` разошлась со сборкой `mmr-gl.js` 0.2.43:

| В документации | В сборке 0.2.43 |
| --- | --- |
| `mmrgl.supported()` — проверка поддержки браузера | метода нет; вызов роняет инициализацию |
| `attributionControl` — «`true` по умолчанию» | по умолчанию `false` |
| логотип не упомянут | `mmrglLogo: true` по умолчанию, угол задаёт `logoPosition`, класс `LogoControl` |
| события `styledata` | есть ещё недокументированное `style.load` — одно на собранный стиль |

**Решение.** При расхождении верим сборке. Необязательные возможности проверяются в рантайме
(`hasSupportedCheck`, `hasLogoControl`), а не предполагаются по документации.

**Последствия.** Плагин работает и на сборках, где часть API отсутствует: проверка поддержки браузера
пропускается, логотип остаётся там, куда его поставил SDK. Расхождения вынесены в вопросы вендору.

**Отвергнуто.** Следовать документации буквально: первая же проверка в браузере показала, что тогда карта не
создаётся вовсе — `mmrgl.supported is not a function`.

## Р-12. Маркеры на web — один слой `symbol`, а не объекты `mmrgl.Marker`

**Дата:** 9 сентября 2026.

**Контекст.** В JavaScript SDK есть класс `Marker` — DOM-элемент поверх карты. Но в контракте плагина маркер
ссылается на картинку в стиле (`imageId`), как устроены нативные SDK, а `Marker` рисует свой HTML и о стиле
ничего не знает.

**Решение.** Все маркеры карты лежат в одном источнике GeoJSON и рисуются одним слоем `symbol`: картинка
берётся выражением `['get', 'imageId']`, точка привязки — `['get', 'anchor']`, порядок — `symbol-sort-key`.
Касание маркера определяется через `queryRenderedFeatures` по этому слою.

**Последствия.** `addStyleImage` работает на web так же, как на мобильных: картинка живёт в стиле, маркер на
неё ссылается. Тысяча маркеров — это один слой, а не тысяча DOM-элементов. Плата: слои приложения, добавленные
без `beforeLayerId`, оказываются поверх маркеров, тогда как на мобильных маркеры всегда сверху.

**Отвергнуто.** `mmrgl.Marker`: пришлось бы либо игнорировать `imageId` и рисовать свой HTML, либо тащить
картинку из стиля в DOM — в обоих случаях web вёл бы себя не так, как остальные платформы.

## Р-13. Состояние стиля хранится в плагине, а вызовы ждут загрузки стиля

**Дата:** 9 сентября 2026.

**Контекст.** `setStyle` в `MMR GL JS` собирает стиль заново и выбрасывает всё, что было добавлено к
предыдущему: источники, слои, картинки. Кроме того, до события загрузки стиля карта отвечает на `addSource`
и `addLayer` ошибкой, а приложение вызывает их сразу в `onMapCreated`.

**Решение.** Web-пакет держит у себя картинки, источники, слои, маркеры и индикатор пользователя. Пока стиль
не собран, вызовы только записываются в это состояние; как только приходит `load` или `style.load` — всё
уезжает в карту. Смена стиля проходит тот же путь.

**Последствия.** Приложение не обязано знать про загрузку стиля и не теряет объекты при его смене — как на
мобильных платформах. Плата: состояние карты хранится дважды, и любая новая операция со стилем должна
попадать и в карту, и в это хранилище.

**Отвергнуто.** Возвращать ошибку «стиль ещё не загружен»: это протекание устройства web-SDK в общий
контракт, которого на других платформах нет.

## Р-14. Данные в web-SDK передаются через `JSON.parse`, а не поэлементной укладкой

**Дата:** 9 сентября 2026.

**Контекст.** Первая версия web-пакета перекладывала словари и списки Dart в JavaScript вручную, по одному
значению. В браузере выяснилось, что часть структур доходила до карты внутренним представлением Dart:
в источнике маркеров вместо объектов GeoJSON лежали `{"a": …, "b": {}, "c": null}`. SDK такие объекты не
разбирает и молча выбрасывает — маркер добавлялся, слой создавался, а на карте не появлялось ничего.

**Решение.** Всё, что уходит в SDK данными — стили, слои, источники, GeoJSON, параметры камеры и элементов
управления, — сериализуется в JSON и разбирается браузерным `JSON.parse`. Проверка типов Dart в этой цепочке
больше не участвует.

**Последствия.** В такие структуры нельзя класть то, что не кодируется в JSON: элементы документа
(контейнер карты, картинка маркера) присваиваются объекту отдельно. Тесты пакета проверяют, что каждая
структура кодируется в JSON целиком — молчаливая порча данных так не повторится.

**Отвергнуто.** `jsify()` и ручная перекладка: обе опираются на проверки типов, которые в собранном для
браузера коде ведут себя иначе, чем в тестах на виртуальной машине, — а ошибка при этом не видна ни
компилятору, ни SDK.

## Р-15. Код, доезжающий до браузера, проверяется в браузере

**Дата:** 9 сентября 2026.

**Контекст.** Декодер закодированной ломаной был написан на побитовых операциях — так он выглядит во всех
известных реализациях. Тесты на виртуальной машине его принимали, а в собранном для web приложении маршрут
длиной 23 км рисовался прямой линией от Москвы к Северному полюсу: в браузере целые числа Dart 32-битные, и
`<<`, `>>`, `~` считают иначе. Ни компилятор, ни анализатор такого не видят.

**Решение.** Пакеты, чей код исполняется в браузере (`vk_maps_mapkit_web` и `vk_maps_api`), прогоняются и
там: `flutter test --platform chrome` и `dart test -p chrome` в `tool/check.sh`. Если Chrome не найден, шаг
пропускается с сообщением, а не роняет проверку. Тесты, которым нужна файловая система, помечаются
`@TestOn('vm')`.

**Последствия.** Проверка стала дольше и требует Chrome. Взамен ошибки, живущие только в браузере, ловятся
